## Вопрос 1

**Какую бизнес-проблему решает этот проект?**

### Суть

Ручная обработка post-purchase обращений требует собрать данные из нескольких источников, сопоставить их и принять решение о маршрутизации.

### Естественная формулировка

> Тут проблема в том, что оператору недостаточно просто посмотреть на сообщение клиента. Нужно ещё получить данные по заказу и доставке, сопоставить их и решить, можно ли этот кейс обработать автоматически или его нужно передать человеку.

### Что важно не утверждать

Не использовать как установленный факт именно этого capstone:

```text
«одно обращение занимает около 12 минут»
```

Не заявлять, что проект уже доказал отсутствие потери точности, ROI или экономию денег.

## Вопрос 2

**Почему в архитектуре выбраны n8n, Python Mock API и deterministic routing logic? Почему не сделать всё одним инструментом?**

### Суть

У компонентов разные роли.

```text
n8n        → orchestration
Python     → mock external APIs
JavaScript → routing logic inside n8n
```

### Естественная формулировка

> Я не стал запихивать всё в один инструмент, потому что здесь разные задачи. n8n у меня отвечает за сам workflow и передачу данных между шагами. Python нужен для отдельных mock API, которые имитируют внешние CRM и carrier. А routing logic я написал на JavaScript внутри n8n, потому что это кодовый узел самого workflow.

### Что важно не говорить

Не говорить, что routing logic написана на Python.

Не утверждать, что выбранный стек является «самым оптимальным» вообще. Здесь корректно говорить о разделении ответственности в рамках этого MVP.

## Вопрос 3

**Почему ты не использовал LLM для самого routing decision?**

### Суть

Routing decision в текущем MVP строится на уже структурированных данных и явных правилах. Поэтому детерминированная logic подходит лучше, чем LLM.

Важно: входящее обращение само по себе не содержит всех данных для решения. В workflow дополнительно приходят `crm_status` и `carrier_status` из двух mock API. Сам routing code использует `crm_status`, `carrier_status` и `request_type`. 

### Естественная формулировка

> Потому что само решение у нас строится по конкретным структурированным данным и понятным правилам. Нам не нужно просить LLM решать, если у нас уже есть `request_type`, статус из CRM и статус от перевозчика. В таком случае проще и предсказуемее использовать обычную deterministic logic. Если бы на входе был свободный текст, LLM можно было бы использовать раньше — чтобы превратить его в структурированный `request_type`, но само routing decision я бы всё равно оставил детерминированным.

### Короткая версия

> LLM здесь не нужен для самого решения, потому что решение основано на структурированных данных и явных правилах. LLM может понадобиться раньше, если входящий запрос нужно сначала нормализовать из свободного текста.

## Вопрос 4

**Что происходит, если CRM и Carrier возвращают разные статусы?**

### Суть

По текущему demo rule рассинхронизация источников не проходит в automatic processing и направляется в `human_handoff`.

### Естественная формулировка

> Если CRM и Carrier возвращают разные статусы, автоматическое продолжение обработки останавливается, фиксируется текущий результат и кейс передаётся на human handoff.

### Что важно уточнить

Это правило относится к текущему **demo-прототипу**. Для production ещё нужно отдельно согласовать reconciliation / source-of-truth policy: какой источник считать приоритетным и что именно делать при конфликте.

## Вопрос 5

**Что именно ты проверял в тестировании?**

### Суть

Проверялись разные входные сценарии, чтобы увидеть фактическое поведение прототипа при разных тестовых inputs. В текущем MVP зафиксированы четыре сценария: automatic processing, `delivery_not_received`, mismatch CRM/Carrier и неизвестный заказ с `404`.

### Естественная формулировка

> Я проверял разные сценарии с разными тестовыми входными данными, чтобы понять, как прототип будет вести себя в каждом случае. В частности, я проверил обычный кейс, где оба источника показывают `delivered`, кейс, где клиент сообщает, что заказ не получил, кейс с расхождением статусов CRM и Carrier и ошибочный кейс с неизвестным заказом.

### Опорные пункты

```text
разные inputs
→ разные сценарии
→ наблюдаемый output
→ проверка routing behavior
```

### Что важно

Эти четыре запуска являются демонстрационными тестами прототипа. Они не являются полноценной статистической оценкой качества системы.

## Вопрос 6

**Какие ограничения у текущего решения?**

### Суть

Первое реальное ограничение, которое ты назвал, — **контракт входных данных**: workflow ожидает определённые поля и значения. Если нужные данные отсутствуют, имеют неверный формат или не соответствуют ожидаемой структуре, обработка может завершиться ошибкой.

Кроме этого, у MVP есть более широкий набор ограничений: внешние CRM и Carrier здесь являются mock-интеграциями, а production authentication, deployment, persistence, monitoring и полноценный error handling пока не реализованы.

### Естественная формулировка

> Первое ограничение — входные данные должны соответствовать тому формату, который ожидает workflow. У нас есть определённые поля и значения, с которыми он умеет работать. Если обязательных данных нет или они некорректные, workflow не сможет нормально продолжить обработку и может завершиться ошибкой.
>
> И кроме этого, сам проект пока является MVP: CRM и Carrier у нас mock-системы, поэтому это ещё не production integration.

### Опорные пункты

```text
input contract
→ обязательные поля / ожидаемые значения
→ некорректный input
→ ошибка или остановка обработки
```

Дополнительно:

```text
mock integrations
+ нет production auth/deployment/monitoring
+ ограниченный error handling
```

### Что важно

Не говорить, что ошибка возникает при любом «неидеальном» значении. Корректнее говорить: данные должны соответствовать ожидаемому контракту конкретного шага и бизнес-правилам workflow.

Также не нужно перечислять все production-ограничения, если интервьюер спрашивает только про конкретный input limitation.

## Вопрос 8

**Какой самый интересный технический баг встретился при реализации?**

### Суть

Во время реализации routing logic использовались ключи, в которых оказался лишний пробел. Из-за этого обращение к ожидаемым полям не совпадало с фактическими ключами данных, и routing logic получала неожиданные / пустые значения.

### Естественная формулировка

> Самый интересный баг был связан с названиями ключей. Там оказался лишний пробел перед закрывающей кавычкой, поэтому workflow обращался не совсем к тому ключу, который мы ожидали. Из-за этого данные дальше не подхватывались, и всё выглядело так, будто логика не работает. Сначала мы долго искали причину, а потом посмотрели на фактический execution output и структуру данных, нашли это несоответствие и исправили названия полей.

### Опорные пункты

```text
routing logic → неожиданные значения
→ проверка execution output / data structure
→ обнаружен лишний пробел в key
→ исправление ключа
→ повторный запуск
→ корректный routing
```

### Почему это хороший пример

Это показывает не просто наличие бага, а способ диагностики: посмотреть на фактические данные, локализовать проблему на уровне структуры и только после этого менять workflow.

В Project Log этот инцидент зафиксирован как скрытый trailing space в `crm_status` / `carrier_status` и отдельно в `request_type`.

## Вопрос 9

**Как ты понимаешь, что automation действительно приносит бизнес-ценность?**

### Суть

Сначала должны быть определены бизнес-требования и критерии успеха. Только после этого можно выбрать и измерять показатели.

Для такого проекта потенциально релевантны:

- время обработки обращения;
- доля обращений, которые workflow может обработать автоматически;
- корректность routing decision;
- доля кейсов, которые действительно доходят до требуемого business completion.

### Естественная формулировка

> Для начала нам нужно определить бизнес-требования и понять, что именно для бизнеса считается успехом. После этого мы можем выбрать метрики. Например, это может быть время обработки обращения, доля обращений, которые workflow обрабатывает автоматически, или процент корректных routing decisions.
>
> Условно, если из тысячи обращений восемьсот после внедрения workflow обрабатываются автоматически, это может быть одним из признаков ценности. Но само по себе число автоматических кейсов ещё не доказывает успех: нужно одновременно проверить, что маршрутизация остаётся корректной и что автоматизация действительно соответствует бизнес-требованиям.

### Опорные пункты

```text
business requirements
→ acceptance criteria / threshold
→ metric
→ baseline
→ actual result
→ business value
```

Пример:

```text
1000 обращений
→ 800 автоматизировано
→ 80% automation rate
```

Но `80%` само по себе ещё не является доказательством успеха.

### Что важно не утверждать

В текущем capstone точные бизнес-метрики, baseline и acceptance threshold ещё не зафиксированы. Поэтому конкретный процент автоматизации, экономию времени или ROI нельзя выдавать за достигнутый результат.
